## 5. Regressions, gaps and deliberate omissions

- **D2 / D3 / D5 came back N/A because no full-scope baseline existed.** This run recorded one
  (`--update-baseline`), so the next run can actually compare. Until then those three gates have
  proved nothing here, and the delta below rests on the Phase-1 SQL snapshot instead
  (`reports/planning/active-tasks/2026-08-31-sharadar-baseline.md`), re-run verbatim after the build.
- **Row count DROPPED 51,608 → 51,255 on purpose.** 353 of those were duplicate `(ticker, as_of)`
  rows produced by amendments; D1 confirms the PK is now unique. A row-count fall is normally a D2
  failure, so it is called out rather than buried.
- **The recovery is +1,265 whole trailing twelves, not the plan's predicted +1,285.** The plan's SQL
  simulation counted CONTIGUOUS windows (exactly 49,500, which reproduced), but 220 of those hold a
  quarter whose vendor `revenue` is absent and `rolling(4)` nulls them by contract. Both numbers are
  right; they count different populations.
- **`totalRevenue` is still NULL on 1,975 rows (3.9%), down from 3,593.** Most are structural — a
  ticker's first three quarters can never have a four-quarter window. **180 gap events remain** in
  the vendor data and are NOT addressed here; a genuinely missing quarter must still null.
- **Four tickers still show a duplicate normalised quarter, and correctly so.** BBY, GPN, KR and OKE
  have 7 groups where TWO REAL quarters normalise onto ONE `calendardate`. De-duplication keys on
  `reportperiod` precisely so these survive; `gate_completeness` fell 316 → 4 tickers, and those 4
  are exactly this carve-out. The roster test asserts the set is EXACTLY those four, so a fifth
  appearing later fails rather than being absorbed.
- **97 genuine restatements are deliberately discarded.** The dedup keeps the EARLIEST filing, which
  is the point-in-time contract — taking the amendment would file a later restatement under an
  earlier publication date. They remain recoverable from `fundamentals_sharadar`, which is lossless.
- **The span tripwire `TTM_SPAN_DAYS = (240, 320)` rejects nothing on today's data**, so it is
  covered only by a synthetic 15-month test, not by real filings. Its LOW edge sits exactly on the
  observed minimum (240 days), so the margin is one-sided: a filer moving to a shorter fiscal
  calendar would be nulled. It logs at WARNING when it fires, so that would be visible.
- **The aggregate fingerprint baseline was NOT regenerated.** The cube reads `fundamentals_history`
  and 1,265 new rows will move it. That baseline is a declared risk zone — it needs explicit
  approval, so it is reported, not fixed.
- **Eight pre-existing test failures are unrelated to this change**, confirmed by running them
  against `HEAD`'s `build_ttm.py` where they fail identically: six in `test_sharadar_field_map.py`
  (SF1 column census, share de-adjustment vs SEC cover page, spinoff-priced split, interest-expense

  (`test_as_of_matches_sec`, `test_axp_revenue_gap_is_detected`). Separately,
